# 从一个任务开始，把设计逐步做实

**状态：原创专题初稿。** 本章依据资料库中 Refactoring UI「Starting from Scratch」五个整理页面的文字与页面图像观察记录编写。图像补阅由主审读者逐页完成，本章作者据记录整理，未再次逐图查看。五页合计28次图片引用观察，其中存在重复图，不能称28幅独立案例。下文三张图为新绘的匿名课程/工作台示意，不是课程截图、真实上线界面或用户测试结果。

开始做一个课程提交工具时，很容易先问：要不要侧栏？卡片是圆角还是直角？用蓝色会不会更专业？这些选择可以影响体验，却还不能回答学习者怎样完成一次提交。

更有用的起点是一句具体任务：**学习者写完一段练习答案，检查内容，然后确认老师收到了哪一版。** 这句话已经包含输入、动作和结果，也暴露了需要决定的事情：提交前能否修改，失败时答案是否保留，成功后能否看见已交版本。先把这些说清楚，布局才有可服务的对象。

## 1. 先画任务骨架

任务骨架不追求画完整产品，只说明完成这件事必需的内容与关系。

| 要素 | 本章原创示例 | 需要确认的问题 |
|---|---|---|
| 情境 | 学习者完成课堂短练习 | 在手机还是电脑上？是否需要录音或附件？ |
| 输入 | 练习编号、答案、提交者身份 | 哪些已经知道，哪些确实需要输入？ |
| 行动 | 检查、修改、提交 | 提交是否不可逆？能否再次提交？ |
| 结果 | 显示已交内容与时间 | 是页面接收了请求，还是服务器已保存成功？ |
| 恢复 | 提交失败后继续修改或重试 | 原答案是否还在？是否会重复提交？ |

本例选择文字提交，是为了说明方法。若真实任务已经要求语音、图片或协作，就不能为了简化而无声删除这些核心能力。缩小范围要发生在承诺明确之前，或与已有范围保持一致。

![原创示意：课程提交从任务骨架进入具体状态，再通过实现和试用继续调整](../assets/diagrams/task-to-flow.svg)

图1把“知道要做什么”与“做出什么状态”连接起来。它增加了失败恢复和试用验证，这两部分属于本章的原创归纳；不能说成来源中的设计—实现示意图已经完整展示了这些步骤。

早期可以用文字、粗线框或简单方块，暂时压低字体、图标和阴影细节。这样做的作用是帮助讨论内容关系，不是证明灰阶一定更好，也不要求所有项目先画同一种线框。已有成熟组件与认可页面时，直接使用它们通常更便于讨论真实状态。

## 2. 把一个任务做成可检查的过程

“最小版本”应当仍能完成承诺的任务。只有一个漂亮的提交按钮，但点击后没有真实结果，不是这项任务的最小完成版本。

在课程提交例子中，第一轮可以只实现一类练习：

1. 显示当前练习及已有答案，避免重复输入已知信息。
2. 让学习者检查和修改内容，说明提交后能否再次修改。
3. 提交时显示真实等待状态，防止重复触发。
4. 成功后展示已交版本及可确认的结果。
5. 失败时保留答案，并给出能执行的恢复动作。

下一轮从实际操作中选择要改的问题。例如用户以为“已提交”表示老师已经批改，就应先修正文案和状态；如果用户一直在寻找“最近一次提交”，结果入口可能需要调整。不能只因为还有空白区域，就增加统计卡片或新导航。

这是一种缩短判断距离的方式：每次改变都对应具体问题，并尽快检查它。它不意味着先发布任何质量的功能；高风险行为、数据丢失和不可逆操作仍需要相应验证。

### 反例：把“以后再做”用于已承诺的核心能力

假设老师明确要求学习者提交发音录音，第一版却只有文字输入。虽然文字表单更容易完成，但它没有完成这次任务。应当先保住必要的录音和结果保存，再考虑是否暂缓装饰、统计或不相关扩展。

另一个反例是只画理想状态。当上传失败时，学生需要重新录整段音频，这种恢复成本比卡片阴影更值得先处理。

## 3. 有限选择要带着用途

当每个按钮都可以从任意颜色、字号和间距中重新挑选，设计很难积累。预先留下少量候选，能让比较更集中，也更容易保持一致。

但只有一排色块还不够。若没有说明颜色用于什么，每次仍然要猜：这一级蓝是按钮、边框还是浅底？本章把来源中的“限制候选”进一步组织为**先定义角色，再为角色选值**。

![原创示意：把有限候选分配给正文、辅助信息、主操作、选中和错误等角色，再放回实际组件检查](../assets/diagrams/choices-by-role.svg)

图2不提供适用于所有产品的固定色阶、字号或像素值。颜色只是示意，字体和间距也需要在实际内容、设备与背景下检查。原生应用优先复用平台和项目已有的语义角色；网页有既有变量时继续沿用，不必另造一套。

可以从反复出现的少数决定开始：

- 正文与辅助说明怎样区分，文字放大后是否仍完整。
- 主操作、选中和错误分别怎样表达，是否还有文字或形状线索。
- 同组内容与不同区块如何拉开距离，是否仍保留足够可见内容。
- 一个图标放进真实按钮后，与文字、基线和点击区域是否协调。

比较候选时，应看组件中的完整关系。孤立的图标看起来顺眼，不代表它放在按钮里仍合适；图形尺寸也不等于可点击范围。候选间相差很小并不总是无关紧要：当文字接近对比度门槛、触控范围或换行边界时，小变化可能产生实际影响。

### 反例：为了统一，强迫所有东西使用同一数值

按钮、消息气泡和大面板可以属于同一视觉系统，却未必需要完全相同的圆角。正文、表单说明和警告也不应仅为“只用三个字号”而牺牲可读性。规则应减少无意义的重复决定，不能消除有理由的情境差异。

## 4. 风格来自多个因素

字体、颜色、图像、形状、留白和语言会共同影响表达。来源中的风格图往往同时改变多个因素，因此只能帮助观察组合差异，不能证明“换成蓝色就更可信”或“圆角越大越亲切”。

为课程提交选择风格时，可以保持核心任务与关键信息不变，再比较不同表达方向。下面三种只是原创方案，尚未做偏好或任务测试。

![原创示意：同一课程提交任务的直接、安静和鼓励三种风格，同时列出文字、颜色和形状的变化](../assets/diagrams/style-as-a-system.svg)

图3中的差异不只有颜色。字体风格、辅助语气与组件形状也在变化。比较时先确认共同底线：任务是否清楚、正文是否可读、操作后果是否完整、错误是否容易修复，再讨论哪一种气质更适合受众。

风格也不必在每个状态保持同一种情绪。开始练习时可以友好，提交失败时应清楚说明发生了什么以及如何继续；不能为了活泼，把重要错误写成只有玩笑和表情。

### 反例：把行业印象当成用户证据

“教育产品就应该可爱”“专业工具必须冷静”都不足以决定方案。面对成人学习者、紧张的考试提交或儿童练习，实际需要可能不同。可以先提出有理由的方向，但仍要观察目标用户能否理解和完成任务。

## 5. 用一轮小验证继续

本章示例尚未进行真人试用；以下是可执行的验证计划，不是已经发生的结果。

| 要判断什么 | 可以怎样查 | 记录什么 |
|---|---|---|
| 任务能否理解 | 让对方先说明页面能做什么，暂不解释 | 原话、误解、缺失的信息 |
| 操作能否完成 | 给出一个实际提交任务，不提示按钮路径 | 实际步骤、犹豫、误点、是否需要帮助 |
| 失败能否恢复 | 在可控测试条件下触发失败 | 答案是否保留，是否知道下一步 |
| 结果是否明确 | 让对方找出已交内容及其状态 | 是否混淆保存、提交、送达和批改 |
| 风格是否合适 | 先完成任务，再询问感受及原因 | 感受与任务表现分开，不只统计“喜欢” |

如果练习本身承担教学目标，还要另外检验学习者能否独立完成相近新题。提交成功只证明提交任务完成，不能证明学会课程内容。

在项目中保留这轮的任务、认可版本、观察与修改理由即可。不要为了采用这套方法，再要求使用者建立一套日常手抄台账。
